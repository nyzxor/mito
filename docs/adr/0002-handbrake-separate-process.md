# ADR-0002: Handbrake as a separate process with a one-directional localhost API

Status: accepted · Date: 2026-09-18

## Context

The Handbrake must be outside the agent's reach: the runtime may not modify policy, budgets,
audit, vault or the kill switch, and the agent must be stoppable within 2 s even if the runtime is
wedged. OpenClaw uses a single Gateway process as control plane; Hermes runs a gateway process
with a non-overridable guard against the agent restarting its own supervisor. Neither separates
"the brakes" from "the agent" at the OS level; we need that separation.

## Options

1. **In-process module** with "please don't import this" conventions. Zero isolation; a
   compromised runtime can monkeypatch anything.
2. **Separate process, same user** (bare Windows dev). Runtime talks to the Handbrake via
   authenticated localhost HTTP; the Handbrake supervises the runtime as a child process.
   Filesystem isolation relies on ACLs/permissions we cannot fully trust on the same user.
3. **Separate container and OS user** (Linux/VPS). Compose network, read-only mounts, the
   runtime container has no route to the internet except via the Handbrake.

## Decision

Option 3 is the production posture; option 2 is the dev posture and is labeled **DEV MODE**
(banner at startup, autonomy capped at A1). Option 1 is rejected.

Protocol: HTTP/1.1 JSON on `127.0.0.1:<port>` (compose: `handbrake:<port>` on an internal
network), bearer token generated by the Handbrake at start and handed to the runtime child via a
file readable only by the runtime user (compose) or via the child's environment (dev). Endpoints
(Phase 1 minimum):

```
POST /gate/dispatch      {session, tool, args, taint, purpose}  → allow|ask|deny + handle
POST /model/call         {session, tier_request, messages_hash, est_tokens} → grant + meter id
POST /model/reconcile    {meter_id, usage}                        → cost posted to ledger
POST /egress/request     {session, method, url, headers, body}    → response (scrubbed, tainted)
GET  /state              → autonomy, metabolic state, halt flag, leash, integrity
POST /halt               {level, nonce}                           (operator token only)
POST /approve|/deny      {action_hash}                            (operator token only)
POST /audit/append       {kind, payload}                          (runtime may append, never read-modify)
```

Two tokens: **runtime token** (can dispatch, call, append) and **operator token** (can halt,
approve, sign, top-up). The runtime never holds the operator token.

Kill path does not go through the API: the Handbrake owns the runtime's process handle
(parent → child) and the Docker client for sandboxes; `hard` = SIGTERM/`TerminateProcess` then
`docker kill` for all containers labeled `mito.session=*`, all within 2 s (tested).

The runtime polls `GET /state` between steps and before every external action; if the Handbrake
is unreachable for >2 s it enters `brake-lost`: no external actions, checkpoint, wait.

## Consequences

- Every tool/model call pays one localhost round-trip (~1 ms); acceptable.
- Two processes to start in dev: `mito up` starts the Handbrake, which starts the runtime.
- Tests can run the Handbrake in-process via its ASGI app for speed, but the 2 s hard-stop test
  runs real processes.

## Dependency cost

ASGI server + HTTP client. Choice: `uvicorn` (server) and `httpx` (client) — both small, async,
mature, cross-platform. We do **not** adopt FastAPI/Starlette for the Handbrake in Phase 1: the
API is ~10 endpoints and pydantic v2 (ADR-0012) already gives validation; a minimal ASGI app keeps
the hash-pinned surface small. Revisit if the dashboard (ADR-0010) needs more.
